# 시나리오 2-08-1: 토큰 한도 재설계(구간 한도 크기와 2단 한도)

**모듈:** 분산 환경 활용 > 서비스 거버넌스
**대상:** `llmd-pd/qwen38-int4-pd`, MaaS 구독 `models-as-a-service/llmd-demo-sub`
**상태:** 실측 완료((a)~(c) 2026-11-05, (d) 2026-11-12)

## 목적

시나리오 2-07은 429의 직접 원인을 "응답 후 차감 + 사용자 단위 고정 구간"으로 확인하였다. 본 시나리오는 구간 한도의 크기와
2단 한도(단기 + 장기)가 에이전트형 부하의 429를 얼마나 줄이는지 측정한다.

## 설정 방법

`MaaSSubscription`의 `tokenRateLimits`에 단기 한도와 장기 한도를 함께 둔다. 단기 한도는 버스트를, 장기 한도는 총량을 통제한다.

```yaml
# MaaSSubscription spec.modelRefs[]
tokenRateLimits:
- limit: 50000      # 단기: 단일 요청 최대 토큰 × 동시 실행 수 이상
  window: 15s
- limit: 80000      # 장기: 총량 예산 (운영에서는 1h 단위 권장)
  window: 2m
```

```sh
oc patch maassubscription llmd-demo-sub -n models-as-a-service --type=json \
  -p '[{"op":"replace","path":"/spec/modelRefs/0/tokenRateLimits","value":[{"limit":50000,"window":"15s"},{"limit":80000,"window":"2m"}]}]'
oc get tokenratelimitpolicy maas-trlp-qwen38-int4-pd -n llmd-pd -o jsonpath='{.spec.limits}'
```

## 실험 설계

| 항목 | 값 |
|---|---|
| 부하 | 에이전트 세션 2개(같은 API 키), 각 세션은 "장문 1건(약 12,100토큰) → 단문 3건"을 90초간 반복 |
| 재시도 | 429 시 1초 후 재시도(일반적인 클라이언트 동작) |
| 비교 한도 | (a) 20,000/15초, (b) 25,000/15초(= 장문 × 동시 2), (c) 50,000/15초, (d) 50,000/15초 + 80,000/2분 |
| 기록 | 429 수, 완료 작업 수, 처리 토큰, 작업 지연(첫 시도~성공), 한 구간 최대 차감량 |

장기 한도는 실험 시간에 맞춰 2분으로 축소하였다. 운영에서는 시간 단위(`1h`)로 둔다.

```sh
cd openshift-ai-llmd-demo/harness
HARNESS_PROFILE=sno MAAS_MIT_ARMS=limit ./harness.sh scenario2-08-mitigation
```

## 결과 (2026-11-05)

| 한도 | 성공 작업 | 시도 | 429 | 처리 토큰 | 작업 지연 p50 | 한 구간 최대 차감 |
|---|---|---|---|---|---|---|
| (a) 20,000/15초 | 24 | 50 | 26 | 86,630 | 8.5초 | 24,532 (1.2배) |
| (b) 25,000/15초 | 27 | 27 | 0 | 98,791 | 2.1초 | 24,802 (1.0배) |
| (c) 50,000/15초 | 27 | 27 | 0 | 98,854 | 2.1초 | 24,901 (0.5배) |
| (d) 50,000/15초 + 80,000/2분 | 27 | 121 | 94 | 98,747 | 2.1초 | 24,829 (0.5배) |

- (a)는 시도의 절반이 429였고 처리량이 약 12% 낮았다. 장문 2건의 차감(약 24.5K)이 한 구간에 들어가 한도를 넘었다.
- (b)는 "장문 최대 토큰 × 세션 수"(12.2K × 2)에 맞춘 한도이며 429가 사라졌다. (c)는 (b)와 같은 결과로, 이 부하에서는
  여유분이 처리량을 늘리지 않는다(처리량은 prefill 속도가 정한다).
- (d)는 15초 한도(50K)에는 한 번도 걸리지 않고 2분 한도(80K)에 걸렸다. 83.5초에 2분 누적이 80K를 넘은 뒤 130.9초까지
  약 48초 동안 두 세션의 모든 요청이 429(94건)였고, 2분 구간 종료(첫 차감 약 11초 + 120초) 직후 복구되었다. 처리 토큰은
  (c)와 같으나 완료까지 143초가 걸렸다.
- 2단 한도는 버스트(15초)는 허용하면서 총량(장기)을 강제한다. 장기 구간이 길수록 한도 소진 후 차단이 길어지므로(2분 구간:
  48초), 장기 한도는 정상 사용에서 닿지 않는 예산 상한으로 두고, 구간은 시간 단위로 둔다.
- (d)의 1차 실행(장기 100,000/2분)은 90초 동안 98,962토큰을 사용하여 장기 한도에 닿지 않았으므로 80,000으로 낮춰 재실행하였다.

## 결론

단기 한도는 버스트를 흡수할 만큼 넉넉히, 장기 한도는 남용을 막는 안전장치로 설계한다.

1. **429의 원인은 서버가 아니라 한도 크기이다.** 단기(15초) 한도를 "단일 요청 최대 토큰 × 동시 실행 수" 이상으로 두면
   성능 손실 없이 429가 사라진다((a) 26건 → (b) 0건, 작업 지연 p50 8.5초 → 2.1초). 고객 사례(100K 요청, 동시 2)에서는
   15초 한도를 200K 이상으로 둔다.
2. **공식값을 넘는 상향은 처리량을 늘리지 않는다.** 처리량은 GPU(prefill 속도)가 정하므로 (c)는 (b)와 같았다. 공식값이
   적정선이다.
3. **총량 통제는 장기 한도로 분리한다.** 장기 한도에 걸리면 구간 종료까지 전면 차단되므로((d) 2분 구간에서 48초), 장기
   한도는 정상 사용에서 닿지 않는 예산 상한으로 두고 구간은 시간 단위(`1h`)로 둔다.
