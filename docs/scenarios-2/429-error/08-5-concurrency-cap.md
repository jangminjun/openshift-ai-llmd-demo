# 시나리오 2-08-5: 세션당 동시 실행 제한

**모듈:** 분산 환경 활용 > 서비스 거버넌스
**대상:** `llmd-pd/qwen38-int4-pd`, MaaS 구독 `models-as-a-service/llmd-demo-sub`
**상태:** 실측 완료(2026-11-12)

## 목적

MaaS는 요청 시작 시 누적만 확인하므로, 동시에 시작한 장문 요청은 모두 통과한 뒤 한도를 크게 넘긴다(2-07 E2: 한도의 2.4배).
초과분은 다음 구간까지 같은 사용자의 모든 요청을 막는다. 본 시나리오는 클라이언트 측 동시 실행 수를 제한했을 때 초과량과
단문의 연쇄 429가 얼마나 줄어드는지, 그 대가로 완료 시간이 얼마나 늘어나는지 측정한다.

## 실험 설계

| 항목 | 값 |
|---|---|
| 한도 | 20,000/15초 (2-07 E2와 같음) |
| 장문 | 6건(약 12,100토큰), 동시 실행 4 / 2 / 1, 429 시 1초 후 재시도 |
| 단문 | 같은 API 키로 1초마다 새 요청(이전 요청 완료를 기다리지 않음), 장문 종료 후 5초까지 |
| 기록 | 한 구간 최대 차감량(한도 대비 배수), 단문의 429 수, 장문 6건의 완료 시간 |

### 동시 실행 제한의 구현 위치

동시 실행 제한은 서버(MaaS, Gateway, vLLM) 설정이 아니라 **클라이언트 측 세마포어**로 구현하였다. MaaS에는 사용자별
동시 요청 수 제한이 없다. `MaaSSubscription`은 토큰 한도(`tokenRateLimits`)만 제공하고, Kuadrant `RateLimitPolicy`는
구간당 요청 수를 셀 뿐 진행 중인 요청 수를 세지 않는다.

probe(클러스터 내 Job)는 장문 6건을 스레드로 동시에 띄우되, `threading.Semaphore(동시 실행 수)`를 얻은 스레드만 요청을
보낸다. 동시 1이면 앞 요청이 끝나야 다음 요청이 출발한다. 429 후 재시도도 세마포어를 쥔 채 수행하므로 동시 실행 수에
포함된다. 단문 probe는 세마포어 밖에서 1초마다 독립적으로 보낸다(장문의 한도 침범을 관측하는 용도).

```python
sem = threading.Semaphore(conc)
def one(i):
    with sem: task(g, f"{i}", words)   # 세마포어를 얻은 작업만 요청 전송
```

따라서 본 실험은 "클라이언트가 세션당 동시 실행을 제한했을 때의 효과"를 측정한다. 실제 적용은 에이전트 프레임워크(세션별
큐·세마포어, 병렬도 설정)에서 해야 하며, 서버가 강제하는 기능은 검증 대상이 아니다.

```sh
cd openshift-ai-llmd-demo/harness
HARNESS_PROFILE=sno MAAS_MIT_ARMS=conc ./harness.sh scenario2-08-mitigation
```

## 결과 (2026-11-12)

| 동시 실행 | 장문 429 | 단문 429 / 시도 | 장문 6건 완료 | 단문 TTFT p50 | 한 구간 최대 차감 |
|---|---|---|---|---|---|
| 4 | 7 | 8 / 74 | 68.9초 | 24.5초 | 25.3K (1.3배) |
| 2 | 2 | 3 / 69 | 64.1초 | 11.9초 | 26.5K (1.3배) |
| 1 | 0 | 0 / 100 | 94.7초 | 5.7초 | 14.1K (0.7배) |

- 동시 실행을 1로 제한하자 장문·단문 모두 429가 사라졌고, 한 구간 차감이 한도 아래(0.7배)로 내려갔다.
- 대가로 장문 6건의 완료 시간이 약 40% 늘었다(64~69초 → 95초).
- 동시 실행 제한은 GPU 경합도 줄여 단문 TTFT를 24.5초에서 5.7초로 낮췄다.
- 동시 2에서 단문 1건이 502를 받았다(원인 미확인).

## 결론

세션당 동시 실행을 1로 제한하면 한도(20K/15초)를 바꾸지 않고도 429가 사라진다. 처리 시간은 늘지만 같은 사용자의 단문
지연도 함께 줄어든다. 한도를 늘릴 수 없는 경우 에이전트 프레임워크에서 세션당 동시 실행을 1~2로 제한한다.

이 제한은 클라이언트가 구현해야 한다. MaaS에는 사용자별 동시 요청 수 제한이 없고(`MaaSSubscription`은 토큰 한도만,
`RateLimitPolicy`는 구간당 요청 수만 집계), 본 실험도 probe의 세마포어로 제한하였다. 고객 환경에서는 에이전트
프레임워크의 세션별 큐·세마포어 또는 병렬도 설정으로 적용한다. 서버가 강제하는 방안으로 llm-d EPP Flow Control의 공정성
큐를 검토할 수 있으나, 사용자별 동시 실행 제한에 쓸 수 있는지는 확인하지 않았다.
